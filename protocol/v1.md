# GY Mahjong WebSocket 协议 v1

状态：草案

本文定义 GY Mahjong 第一版可游玩的 WebSocket 协议。v1 的范围刻意保持精简：客户端创建或恢复临时会话、加入固定房间 `room-001`、准备、接收自己的牌桌快照并提交动作，以及主动交给 AI 代管与返回。动态建房、观战、聊天和牌谱下载不属于 v1。

服务端是唯一权威。客户端请求只表达操作意图；收到新的服务端快照前，客户端不能自行增减牌张、判断合法操作或修改分数。

## 1. 传输与消息信封

- 每个 WebSocket 文本消息承载一个 JSON 对象。
- 拒绝 WebSocket 二进制消息。
- 文本统一使用 UTF-8。
- 单条消息最大 64 KiB，JSON 最大嵌套深度为 32。
- 每条消息都包含整数 `v` 和字符串 `type`，其中 `v` 固定为 `1`。
- 未知消息类型、未知字段、未知枚举值和错误字段类型均被拒绝。只有明确标记为可选的字段才允许缺失。
- `hello` 成功后，服务端可以随时主动推送消息，客户端不能假设所有消息都是严格的一问一答。

消息信封示例：

```json
{"v":1,"type":"ping","nonce":"browser-17"}
```

### 1.1 整数编码

所有对应 C++ `uint64_t` 和 `int64_t` 的值都使用 JSON 十进制字符串，避免 JavaScript `Number` 丢失精度。

合法示例：`"0"`、`"1"`、`"18446744073709551615"`。

非法示例：`1`、`-1`、`"01"`、`"1.0"`、`"+1"`、`" 1"`。

前端可以用 `BigInt` 处理这些值，但执行 `JSON.stringify` 前必须转换回字符串。座位号、牌山剩余数量、超时毫秒数和协议版本等较小数值使用 JSON 整数。

### 1.2 牌面编码

可见牌使用两个字符表示：

- `1m` 至 `9m`：万子
- `1s` 至 `9s`：索子
- `1p` 至 `9p`：筒子

当前规则没有字牌。不存在或需要隐藏的牌使用 `null`。要求指定牌面的客户端动作必须提供合法牌面字符串，不能发送 `null`。

### 1.3 动作编码

| 协议值 | C++ 值 | `tile` 字段 |
| --- | --- | --- |
| `discard` | `Discard` | 必填 |
| `pon` | `Pon` | 必填 |
| `self_kan` | `SelfKan` | 必填 |
| `add_kan` | `AddKan` | 必填 |
| `open_kan` | `OpenKan` | 必填 |
| `tsumo` | `Tsumo` | 省略 |
| `ron` | `Ron` | 省略 |
| `pass` | `Pass` | 省略 |

当前规则不支持吃牌，因此 `chi` 会被拒绝。

```json
{"type":"discard","tile":"5m"}
```

```json
{"type":"pass"}
```

## 2. 连接生命周期

```text
WebSocket 已连接
  -> hello
  -> welcome
  -> join_room
  -> table_update
  -> ready
  -> table_update（四人准备后由服务端开局）
  -> action / table_update / ack
  -> 断线，或使用 sessionToken 重连
```

`hello` 成功前只允许发送 `hello` 和 `ping`。会话入座后，房间和内部玩家身份都来自服务端会话绑定。客户端提交的字段不能用于选择玩家或座位。

## 3. 客户端消息

### 3.1 `hello`

`hello` 必须是新连接上的第一条业务消息。创建临时会话时发送昵称：

```json
{"v":1,"type":"hello","nickname":"玩家甲"}
```

恢复已有临时会话时发送令牌：

```json
{"v":1,"type":"hello","sessionToken":"64个小写十六进制字符"}
```

`nickname` 和 `sessionToken` 互斥。昵称去除首尾空白后必须包含 1 至 24 个 Unicode 标量值，且不能包含控制字符。昵称不要求唯一。

会话令牌由服务端使用至少 256 位密码学安全随机数生成，不能包含内部 `PlayerInfo.id`、时间戳或可预测序列。

成功响应：

```json
{
  "v": 1,
  "type": "welcome",
  "sessionToken": "8f0c...总计64个十六进制字符...a921",
  "resumed": false,
  "nickname": "玩家甲",
  "roomId": null
}
```

当 `resumed` 为 `true` 且玩家已经入座时，`roomId` 为绑定房间；服务端紧接着发送一条 `table_update`。使用同一有效令牌建立第二条连接时，新连接接管会话，旧连接此后到达的消息和关闭回调都不能再影响该会话。

### 3.2 `ping`

`ping` 可以在 `hello` 前后发送。可选的 `nonce` 最长为 64 字节，服务端原样返回。

```json
{"v":1,"type":"ping","nonce":"browser-17"}
```

```json
{"v":1,"type":"pong","nonce":"browser-17"}
```

这个应用层消息不能替代 WebSocket 协议自身的 ping/pong 控制帧。

### 3.3 `join_room`

要求已经完成 `hello`。v1 只接受 `room-001`。

```json
{
  "v": 1,
  "type": "join_room",
  "requestTag": "join-1",
  "roomId": "room-001"
}
```

`requestTag` 是客户端生成的 1 至 64 字节不透明字符串，用于关联响应。加入成功后，服务端先发送 `ack`，再发送一条或多条 `table_update`。重试同一请求不能重复分配座位。

### 3.4 `ready`

要求会话已经入座。消息中的 `roomId` 只用于一致性检查，必须与会话绑定一致。

```json
{
  "v": 1,
  "type": "ready",
  "requestTag": "ready-1",
  "roomId": "room-001"
}
```

四个座位都入座且准备后（含 AI 自动准备），服务端只调用一次 `Table::start()`。AI 在局外自动准备，真人手动准备；至少有一名真人留在桌上才允许继续，全员离开立即关局。即使后续自动开局失败，准备请求本身仍可能成功；开局失败通过单独的 `server_notice` 报告。

### 3.5 `snapshot`

请求当前已认证玩家的最新私有视角。

```json
{
  "v": 1,
  "type": "snapshot",
  "requestTag": "snapshot-4",
  "roomId": "room-001"
}
```

服务端返回 `ack` 和 `table_update`。快照是完整状态，客户端应直接替换当前牌桌状态。

### 3.6 `action`

要求会话已经入座，并且最新快照中存在有效操作窗口。

```json
{
  "v": 1,
  "type": "action",
  "roomId": "room-001",
  "roundId": "1",
  "requestId": "7",
  "promptId": "18",
  "action": {"type":"discard","tile":"5m"}
}
```

字段对应 `gymj::common::Command`：

| 字段 | 含义 |
| --- | --- |
| `roundId` | 最新私有快照中的小局编号 |
| `requestId` | 玩家在同一小局中严格递增的请求编号 |
| `promptId` | 最新快照中的操作窗口编号 |
| `action` | `availableActions` 中列出的一个动作 |

服务端从已认证会话获取 `PlayerInfo`，绝不从 JSON 获取玩家身份。`roomId` 必须与会话绑定一致。

每个新动作都必须使用新的 `requestId`，包括上一个动作被拒绝的情况。客户端可以使用相同 `requestId` 重发内容完全相同的命令；服务端返回缓存结果，但不能再次执行。使用相同 `requestId` 提交不同内容会被拒绝。

### 3.7 `leave_room`

要求已经完成 `hello`，身份由当前连接的会话确定，不能指定座位或玩家 ID：

```json
{"v":1,"type":"leave_room","requestTag":"leave-1","roomId":"room-001"}
```

所有阶段均允许交给 AI，包括 `playing`。成功后先返回 `operation: "leave_room"`
的成功 `ack`，再向仍由真人控制的座位发送 `table_update`。客户端清空本地牌桌并进入
`away`（AI 代管）状态，保留 `roomId`；这不是未入座状态。

- 原身份、房间、座位、累计分、请求水位和操作期限保持不变，其他玩家不能补位。
- 已占用座位的 `connected: false` 表示 AI 代管；主动交接后 WebSocket 可以仍然连接。
- AI 沿用超时出牌/过牌策略，并在等待准备和每次结算后自动准备；真人仍需手动准备。
  四个座位准备齐且仍有真人在桌上才开下一局；所有已入座真人均离开后关闭牌桌。
- 原连接不再收到主动快照广播；`ready` 和 `action` 返回失败的 `ack`，错误为
  `action_not_allowed`。原身份仍能请求 `snapshot`，但快照请求不会接回控制。
- 发送 `join_room` 接回原座位；恢复令牌时 `welcome.resumed` 为 `true`，`roomId`
  为原房间，随后主动发送最新私有快照并恢复真人控制。刷新可能恢复到之后的小局。
- 重复交接不改变牌桌；未入座身份对有效房间请求交接也返回成功。`requestTag` 仅关联回执，
  返回后不能重放旧的交接请求。AI 已提交的准备在返回时保持有效。
- 最后一名真人主动离开或断线后立即关局（未满四人的等待桌也适用）；AI 不再推进或准备。
  仍打开的旧桌连接收到 `server_notice`，`code: "room_closed"`。主动离开的成功 `ack`
  先于关局通知发送。客户端清空牌桌与凭据并断开连接，不再显示可返回原座位。
- 该桌全部旧令牌失效，之后用 `hello.sessionToken` 恢复返回 `session_expired`；
  已打开的旧连接也失去认证，不能直接 `join_room`、`snapshot` 或 `action` 恢复旧桌。
- 固定地址 `room-001` 可供新身份创建全新的牌桌：局号和累计分重新开始，使用独立牌谱。
  未完成的小局仅记录终止，不伪造正常结算。
- 不增加限制玩家另开对局的身份规则；动态建房仍不属于当前单房间版本。

## 4. 服务端消息

### 4.1 `ack`

大厅类命令回执：

```json
{
  "v": 1,
  "type": "ack",
  "operation": "join_room",
  "requestTag": "join-1",
  "accepted": true,
  "error": null
}
```

`operation` 为 `join_room`、`leave_room`、`ready` 或 `snapshot`。

动作回执：

```json
{
  "v": 1,
  "type": "ack",
  "operation": "action",
  "requestId": "7",
  "accepted": true,
  "duplicate": false,
  "tableSeq": "31",
  "error": null
}
```

`accepted` 只描述请求的牌桌状态转移是否被接受。牌谱存储告警不能把已经接受的动作改成拒绝；存储问题通过 `server_notice` 单独发送。

### 4.2 `table_update`

`table_update` 包含完整私有快照，以及可选的动画事件：

```json
{

  "type": "table_update",
  "roomId": "room-001",
  "view": {
    "selfSeat": 0,
    "tableStage": "playing",
    "roundStage": "waiting_discard",
    "tableSeq": "31",
    "roundId": "1",

    "promptId": "18",

    "dealerSeat": 0,
    "tilesRemaining": 55,

      {
        "occupied": true,
        "connected": true,

      "hand": ["1m", "1m", "2m", "3m", "4s", "5s", "6s", "2p", "3p", "4p", "7p", "8p", "9p"],

    }

```

上面的数值只用于展示字段格式，不代表一组完整合法的牌局状态。

#### 视角枚举

`tableStage`：`waiting_ready`、`playing`、`round_finished`。

`roundStage`：`not_active`、`waiting_draw`、`waiting_discard`、`waiting_claim`、`ended`。

副露 `type`：`pon`、`open_kan`、`self_kan`、`add_kan`。

`remainingMs` 是服务端单调时钟计算出的非负 JSON 整数。当前玩家没有操作期限时为 `null`。前端倒计时归零后，最终超时判定仍由服务端负责。

`actingSeat` 等可选座位字段在不适用时为 `null`。合法座位是整数 `0` 至 `3`。

`oneSou` 和 `eightPin` 存在时使用以下结构：

```json
{
  "tile": "1s",
  "discardedBy": 2,
  "claimedBy": null,
  "claimType": null
}
```

#### 小局结果

对局进行中 `roundResult` 为 `null`。小局结束后使用以下结构：

```json
{
  "hasWinner": true,
  "winnerSeats": [1],
  "discarderSeat": 3,
  "winTile": "5m",
  "winType": "ron",
  "winDetail": "simple",
  "states": [
    {"hand":["1m"],"river":[],"melds":[],"drawBuffer":null,"discardBuffer":null},
    {"hand":["2m"],"river":[],"melds":[],"drawBuffer":null,"discardBuffer":null},
    {"hand":["3m"],"river":[],"melds":[],"drawBuffer":null,"discardBuffer":null},
    {"hand":["4m"],"river":[],"melds":[],"drawBuffer":null,"discardBuffer":null}
  ],
  "oneSou": null,
  "eightPin": null,
  "roundChicken": "7p",
  "chickenIndicator": "6p"
}
```

`states` 固定包含四家的最终牌面，仅在小局结束后公开。`winType` 为 `no_winner`、`ron` 或 `tsumo`。`winDetail` 为 `no_winner`、`simple`、`tsumo_from_kan`、`ron_kan_discard` 或 `ron_add_kan`。没有赢家时，不适用的座位和牌面使用 `null`，不能使用 `-1` 或非法牌面字符串。

#### 小分结果

分数计算完成前 `pointResult` 为 `null`。所有分数都使用十进制字符串：

```json
{
  "delta": ["9", "-3", "-3", "-3"],
  "toOthers": [
    ["0", "3", "3", "3"],
    ["-3", "0", "0", "0"],
    ["-3", "0", "0", "0"],
    ["-3", "0", "0", "0"]
  ],
  "detail": [
    {"total":"9","chicken":"0","kan":"0","agari":"9","tenpai":"0"},
    {"total":"-3","chicken":"0","kan":"0","agari":"-3","tenpai":"0"},
    {"total":"-3","chicken":"0","kan":"0","agari":"-3","tenpai":"0"},
    {"total":"-3","chicken":"0","kan":"0","agari":"-3","tenpai":"0"}
  ]
}
```

实际分值由服务端规则决定，客户端只负责展示。

#### 事件枚举

事件 `type` 可以是 `round_started`、`initial_hands`、`player_draw`、`player_discard`、`meld_declared`、`add_kan_proposed`、`player_win`、`round_ended`、`points_calculated` 或 `chicken_revealed`。

`claim_submitted` 不发送给客户端，因为它会泄露其他玩家尚未裁决的操作。事件中不适用的字段使用 `null` 或空数组。

快照是完整且权威的状态。`events` 只用于播放动画，客户端不能再用它们重复修改同一条消息中的快照。服务端必须通过公开字段白名单构造网络事件，不能直接序列化权威 `RoundState` 或未经脱敏的 `RoundEvent`。

### 4.3 `server_notice`

不需要玩家操作的服务状态通过独立消息报告：

```json
{
  "v": 1,
  "type": "server_notice",
  "code": "replay_write_failed",
  "message": "牌谱保存失败，请联系管理员"
}
```

`message` 可以直接展示，但客户端逻辑必须依据 `code`。消息不能包含令牌、内部路径、异常文本或隐藏牌。

### 4.4 `error`

协议、认证和路由错误使用统一结构：

```json
{
  "v": 1,
  "type": "error",
  "code": "invalid_tile",
  "requestTag": null,
  "requestId": "7",
  "message": "牌的格式无效"
}
```

只有当 `requestTag` 或 `requestId` 本身足够合法、可以安全回显时才包含对应字段。`message` 是可选展示文本，客户端逻辑使用稳定的 `code`。

| 错误码 | 含义 |
| --- | --- |
| `invalid_json` | 消息不是合法 JSON 对象 |
| `json_too_deep` | JSON 嵌套超过限制 |
| `text_only` | 收到 WebSocket 二进制消息 |
| `unsupported_version` | `v` 缺失或不为 `1` |
| `invalid_type` | `type` 缺失或不是字符串 |
| `unknown_type` | v1 未定义该消息类型 |
| `invalid_field` | 字段缺失、未知或类型错误 |
| `invalid_tile` | 牌面字符串不属于 v1 牌面集合 |
| `invalid_action` | 动作未知或 `tile` 结构错误 |
| `hello_required` | `hello` 前发送了业务请求 |
| `already_authenticated` | 同一连接重复发送 `hello` |
| `invalid_nickname` | 昵称长度或字符不合法 |
| `invalid_session` | 会话令牌格式错误 |
| `session_expired` | 会话令牌未知或已过期 |
| `not_seated` | 请求要求玩家已经入座 |
| `room_not_found` | 房间不存在 |
| `room_mismatch` | 请求房间与会话绑定不一致 |
| `room_full` | 房间没有空位 |
| `already_in_room` | 会话已经绑定其他房间 |
| `stale_round` | `roundId` 与当前小局不一致 |
| `stale_prompt` | `promptId` 与当前操作窗口不一致 |
| `stale_request` | `requestId` 不是合法新请求或重复请求 |
| `action_not_allowed` | 当前玩家不能执行该动作 |
| `rate_limited` | 连接或会话超过限流阈值 |
| `internal_error` | 未向客户端暴露细节的服务端错误 |

无效业务请求通常不会关闭 WebSocket。对于超过大小或频率限制、持续发送畸形消息的连接，服务端可以主动关闭。

## 5. 顺序、重连与客户端状态

- `tableSeq` 用于排序牌桌快照。客户端忽略比当前已应用快照更旧的 `tableSeq`。
- 一次牌桌操作产生的多个 `Delivery` 必须按原顺序发送，并使用各自 `view.tableSeq`。
- `action` 回执与对应的 `table_update` 是两条独立消息。服务端在请求连接上先发送回执。
- 重连后，客户端必须等到 `welcome` 和最新 `table_update` 后才能重新启用操作控件。
- 快照中的 `lastRequestId` 是该玩家的服务端请求水位。下一个新动作使用更大的编号。
- 客户端断线后不能自动重放全部点击，只能精确重试仍在途的同一命令，或重新请求快照。
- 断线或 `leave_room` 将原座位交给 AI 持续代管并自动准备，不释放座位、不允许补位。在原桌仍有真人时，恢复原令牌或发送 `join_room` 接回原座位；全员离开后旧令牌失效。

## 6. 隐私与信任边界

- 会话令牌是唯一的重连凭据，由服务端保存在内存中；v1 前端建议存入浏览器 `sessionStorage`。
- 会话令牌不能写入日志、URL、牌谱文件或错误消息。
- 内部玩家 ID 和 `Delivery.recipient_id` 永远不发送给客户端。
- 客户端不能提交座位号或玩家 ID 来选择动作执行者。
- 对手暗手和摸牌不能出现在当前玩家的私有快照或事件中。
- 对手的暗杠在规则公开前使用 `tile: null`。
- 生产环境使用 `wss://`，本地开发可以使用 `ws://`。

## 7. 最小验收测试

1. 四个独立会话加入 `room-001`、完成准备，并收到四份不同的私有开局快照。
2. 第五个会话收到 `room_full`，且牌桌状态不发生变化。
3. 一次合法出牌只改变一次状态；精确重试被标记为重复，不能再次出牌。
4. 非法牌面、动作、整数字符串、旧小局和旧操作窗口都不能改变牌桌状态。
5. 伪造房间、座位、玩家和令牌不能操作其他座位。
6. 任意玩家收到的消息都不能包含其他玩家的暗牌或私有合法操作。
7. 使用令牌重连后恢复原座位，新连接替换旧连接，且操作截止时间不被重置。
8. 现有核心测试和 WebSocket 传输测试继续通过。
